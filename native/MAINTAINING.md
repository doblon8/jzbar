# Maintaining the native libraries

How to rebuild, upgrade and re-record the native libraries bundled in jzbar.
To build a replacement library for your own use, see `BUILDING.md` instead.

## What is where

| Path | Purpose |
| --- | --- |
| `native/sources.env` | Pinned ZBar and libiconv versions and SHA-256 hashes, plus `SOURCE_BUNDLE_URL`, the published location of this release's source bundle. Read by every script. |
| `native/build-windows-x64.sh`, `build-linux.sh`, `build-macos.sh` | The builds. Run by the workflows in `.github/workflows/native-*.yaml`. |
| `native/lib.sh` | Helpers shared by the scripts (not run directly). With `NATIVE_SOURCES_DIR` set, the build scripts take the upstream tarballs from that directory instead of downloading them. |
  | `native/meson-requirements.txt`, `native/ninja-requirements.txt` | Hash-pinned meson (Linux, macOS) and ninja (macOS) wheels from PyPI; ZBar 0.23.94 and later builds with meson (0.61 or newer). On Windows, meson and ninja come from MSYS2 and are not pinned. |
| `native/write-manifest.sh` | Writes `native/manifest/<platform>.manifest` from a workflow artifact. |
| `native/check-manifests.sh` | Checks that the committed binaries and license texts match the manifests and `SHA256SUMS`. Runs in CI. |
| `native/make-notices.sh` | Generates `THIRD-PARTY-NOTICES` from the manifests and `SOURCE_BUNDLE_URL`. CI regenerates it and fails on any difference. |
| `native/manifest/` | One manifest per platform: sources, toolchain, output hashes, run URL. |
| `native/extract-licenses.sh` | Regenerates `native/licenses/zbar/`, `native/licenses/libiconv/` and `native/licenses/SHA256SUMS` from the pinned tarballs. |
| `native/licenses/` | License texts of what is linked into the binaries, with `SHA256SUMS` and a `README.md` saying where each text came from. |
| `native/make-source-bundle.sh` | Builds the source bundle for a release (pinned tarballs, scripts, workflows, manifests, licenses). |
| `src/main/resources/native/` | The committed binaries that end up in the JAR. |

Platforms: `windows-x64`, `linux-x64`, `linux-aarch64`, `macos-x64`, `macos-aarch64`.
Each manifest lists its binaries by path relative to `src/main/resources/native`:

| Platform | Files |
| --- | --- |
| `windows-x64` | `windows/x64/zbar.dll`, `windows/x64/libiconv-2.dll` |
| `linux-x64` | `linux/x64/libzbar.so` |
| `linux-aarch64` | `linux/aarch64/libzbar.so` |
| `macos-x64` | `osx/x64/libzbar.dylib` |
| `macos-aarch64` | `osx/aarch64/libzbar.dylib` |

## Rules

- Binaries are committed. CI does not rebuild them on release, it only checks them against the manifests.
- ZBar's meson build hides internal symbols only on Linux (the version script `zbar/zbar.map`). The macOS and Windows scripts restrict the exports to the same names, as ZBar 0.23.93 did. Do not remove that: those binaries would export about 100 internal symbols more than the Linux one.
- On Windows the exports are restricted by linking again with `--exclude-symbols`, not with a `.def` file: meson re-runs its configure-time checks with the same link arguments, and a `.def` file makes them fail.
- Manifests are generated by `write-manifest.sh` from the artifacts of the run that produced the binaries. Do not edit them by hand.
- A manifest records what the build saw, not proof of it. Binaries and manifest must always be committed together.
- Do not remove the determinism settings in the Windows build (`--no-insert-timestamp`, the fixed `--image-base`, `SOURCE_DATE_EPOCH=0`). Without them the DLLs differ on every run.
- Keep editor backup files (`*~`) out of `native/licenses/`. `.gitignore` covers them, and `extract-licenses.sh` only hashes files that git knows about.

## Upgrading ZBar or libiconv

1. **Check the new tarball.**
   - ZBar publishes no signature. Compare the tarball with the git tag of the same version (`mchehab/zbar`) and note any differences in `.c` and `.h` files. Since 0.23.95 the tarball contains no generated files, so it should equal git archive <tag>. The tag is signed: import the maintainer’s key and run git tag -v, and confirm the fingerprint against kernel.org’s pgpkeys repository.
   - libiconv is GPG-signed. Verify the signature and cross-check the signer's fingerprint and the tarball hash against an independent packager (for example Arch's `libiconv` package).
2. **Edit `native/sources.env`.** Change `*_VERSION` and `*_SHA256` together, and `ICONV_GPG_FPR` if the signer changes. Update the provenance comment with what you checked, the date and the URLs.
3. **Check the build flags.** Compare the `meson setup` options in the three scripts with the new version's `meson.options` (`meson configure <builddir>` lists them with defaults). A renamed option makes `meson setup` fail, but a new option that defaults to enabled is silent, so read the `Features` summary meson prints (all `NO`). If `zbar/zbar.map` changed, the export lists derived from it change too. For libiconv (Windows only), diff `./configure --help` of the old and new versions, and review any flag that works around a toolchain problem (for example `-std=gnu17`).
4. **Build twice.** Push the branch, then run each workflow (`Native: Windows x64`, `Native: Linux`, `Native: macOS`) two times from the Actions tab.
   - The two runs of each workflow must print identical hashes. If they don't, find out why before going on.
   - Then compare exports, imports and dependencies with the committed binaries (see the next section).
5. **Install the binaries.** Download the artifacts (`windows-x64`, `linux-x64`, `linux-aarch64`, `macos-x64`, `macos-aarch64`) and copy the binaries to the paths in the table above.
6. **Write the manifests.** Unpack each artifact into its own directory and run, with the commit and run URL of the second run:
```bash
   WORKFLOW_COMMIT=<commit the workflow ran at> \
   WORKFLOW_RUN_URL=https://github.com/doblon8/jzbar/actions/runs/<run id> \
   native/write-manifest.sh <platform> <artifact directory>
```
   The Linux and macOS workflows each produce two artifacts from one run, so use the same commit and run URL for both architectures. The commit must be pushed and available locally.
7. **Save the logs.** Logs expire after 90 days. For each of the three runs cited in the manifests, save the log archive and keep it as an asset of the release that ships these binaries (not in the repository):
```bash
   gh api repos/doblon8/jzbar/actions/runs/<run id>/logs > run-<run id>-logs.zip
   sha256sum run-<run id>-logs.zip
```
8. **Update the test.** Change the expected `ZBar.version()` string in `ZBarTest`.
9. **Licenses.** Run `native/extract-licenses.sh` to replace the texts taken from the tarballs and regenerate `native/licenses/SHA256SUMS`. Read the diff: a changed `COPYING` in ZBar can mean a new notice or exception. If it mentions code under another license, add its text by hand and record where it came from in `native/licenses/README.md`. Then run `native/make-notices.sh` to regenerate `THIRD-PARTY-NOTICES`.
10. **Check.** Run `native/check-manifests.sh` locally, then push and wait for CI. The test matrix runs on all five platforms.
11. **Commit** the binaries, the manifests, the license changes and `THIRD-PARTY-NOTICES` together.

## Comparing a new build with the committed binaries

Set `LC_ALL=C` so that sorting matches. Take the old binary from `src/main/resources/native` or from the previous tag (`git show v<old>:<path>`).

  | Platform | Exports | Dependencies |
  | --- | --- | --- |
  | Linux | `nm -D --defined-only lib \| awk '{print $3}' \| sort` | `readelf -d lib \| grep -E 'SONAME\|NEEDED'`; `objdump -T lib \| grep -o 'GLIBC_[0-9.]*' \| sort -Vu \| tail -1` |
  | macOS | `llvm-nm -gU lib \| awk '{print $3}' \| sort` | `llvm-otool -L lib` |
  | Windows | `llvm-readobj --coff-exports dll \| grep 'Name:' \| sed 's/.*Name: //' \| sort` | `llvm-readobj --coff-imports dll \| grep -E 'Name:\|Symbol:'` |

The exports must be identical unless upstream changed its public API; extra exports mean the export restriction stopped working. The libiconv import hints in `zbar.dll` change whenever libiconv's export table changes, which is harmless.

## Rebuilding without changing versions

Use this when you want to know whether the committed binaries still reproduce, for example after a runner image update.

1. Run the three workflows and compare the printed hashes with `native/manifest/*.manifest`.
2. If they match, nothing to do.
3. If they differ, compare the artifact's `toolchain.txt` with the manifest. A different compiler, linker, libc or SDK version explains a different hash. The packages are logged but not pinned (MSYS2, apt), so a package update changes bytes without any change in the scripts.
4. If the toolchain is identical and the hash differs, the build is no longer deterministic. Investigate before releasing anything.
5. Replace the committed binaries only for a reason. If you do, follow steps 4 to 11 above (the sources are unchanged).

## Changing the toolchain pins

- Linux containers: the `container:` of each matrix entry in `.github/workflows/native-linux.yaml`, pinned by digest: Ubuntu 20.04 for x64 (glibc 2.31, so the binary loads on older distros) and Ubuntu 24.04 for aarch64 (the target Sparrow Wallet uses). The manifest records it. Dependabot does not update it.
- meson and ninja (Linux, macOS): `native/meson-requirements.txt` and `native/ninja-requirements.txt`, pinned by version and wheel hash. To update, take the hashes from `https://pypi.org/pypi/<name>/<version>/json`, check `Requires-Python` against the Python of the Linux containers (3.8 on Ubuntu 20.04), and rebuild twice. On Windows they are MSYS2 packages, not pinned.
- Actions: pinned by commit SHA in every workflow, with the version in a comment on the same line. Dependabot (`.github/dependabot.yml`) opens pull requests for updates. After merging one that touches a native workflow, run the three workflows and compare the hashes with the manifests. An Actions update should not change the binaries, but nothing else checks that.
- Anything that changes the toolchain changes the manifest, so rebuild twice and regenerate the manifests.

## Source bundle

`native/make-source-bundle.sh VERSION [output-dir]` builds `jzbar-native-sources-VERSION.tar.gz` from the committed state of the repository: the pinned ZBar and libiconv tarballs (checked against `sources.env`), `native/`, the three native workflows, `LICENSE`, `THIRD-PARTY-NOTICES`, `BUILDING.md` and `BUNDLE-INFO.txt` (version and commit). It fails if those paths have uncommitted changes.

- The same commit gives the same bundle, so you can build it twice and compare hashes.
- To build from a bundle without network access to the upstream sites, unpack it and set `NATIVE_SOURCES_DIR=<bundle>/sources` before running a build script.
- Publish it with the release, next to the JAR, and keep it with the logs from step 7.

## Releasing

1. Set the release version in `pom.xml`.
2. Set `SOURCE_BUNDLE_URL` in `native/sources.env` to `https://github.com/doblon8/jzbar/releases/download/v<version>/jzbar-native-sources-<version>.tar.gz`, then run `native/make-notices.sh`. CI fails if the URL and the pom version disagree.
3. Commit, push and wait for CI to pass on `main`.
4. Run `mvn clean install` and test the JAR in a consumer project before tagging.
5. From the clean tree, run `native/make-source-bundle.sh <version> /tmp/out`. Keep its SHA-256 for the release notes.
6. Tag that commit as `v<version>` and push the tag.
7. Create the GitHub release and attach the bundle and, if the binaries changed in this release, the log archives from step 7 of "Upgrading ZBar or libiconv". Save the logs before they expire, 90 days after each run.
8. Publish to Maven Central.
