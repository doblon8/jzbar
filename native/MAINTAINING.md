# Maintaining the native libraries

How to rebuild, upgrade and re-record the native libraries bundled in jzbar.
To build a replacement library for your own use, see `BUILDING.md` instead.

## What is where

| Path | Purpose |
| --- | --- |
| `native/sources.env` | Pinned ZBar and libiconv versions and SHA-256 hashes. Read by every script. |
| `native/build-windows-x64.sh`, `build-linux.sh`, `build-macos.sh` | The builds. Run by the workflows in `.github/workflows/native-*.yaml`. |
| `native/lib.sh` | Helpers shared by the scripts (not run directly). |
| `native/write-manifest.sh` | Writes `native/manifest/<platform>.manifest` from a workflow artifact. |
| `native/check-manifests.sh` | Checks that the committed binaries and license texts match the manifests. Runs in CI. |
| `native/manifest/` | One manifest per platform: sources, toolchain, output hashes, run URL. |
| `native/licenses/` | License texts of the components linked into the Windows DLL. |
| `src/main/resources/native/` | The committed binaries that end up in the JAR. |

Platforms: `windows-x64`, `linux-x64`, `linux-aarch64`, `macos-x64`, `macos-aarch64`.
Each manifest lists its binaries by path relative to `src/main/resources/native`:

| Platform | Files |
| --- | --- |
| `windows-x64` | `windows/x64/zbar.dll`, `windows/x64/libiconv-2.dll` |
| `linux-x64` | `linux/x64/libzbar.so` |
| `linux-aarch64` | `linux/aarch64/libzbar.so` |
| `macos-x64` | `osx/x64/libzbar.dylib` |
| `macos-aarch64` | `osx/aarch64/libzbar.dylib` |

## Rules

- Binaries are committed. CI does not rebuild them on release, it only checks them against the manifests.
- Manifests are generated by `write-manifest.sh` from the artifacts of the run that produced the binaries. Do not edit them by hand.
- A manifest records what the build saw, not proof of it. Binaries and manifest must always be committed together.
- Do not remove the determinism settings in the Windows build (`--no-insert-timestamp`, the fixed `--image-base`, `SOURCE_DATE_EPOCH=0`). Without them the DLLs differ on every run.

## Upgrading ZBar or libiconv

1. **Check the new tarball.**
   - ZBar publishes no signature. Compare the tarball with the git tag of the same version (`mchehab/zbar`) and note any differences in `.c` and `.h` files.
   - libiconv is GPG-signed. Verify the signature and cross-check the signer's fingerprint and the tarball hash against an independent packager (for example Arch's `libiconv` package).
2. **Edit `native/sources.env`.** Change `*_VERSION` and `*_SHA256` together, and `ICONV_GPG_FPR` if the signer changes. Update the provenance comment with what you checked, the date and the URLs.
3. **Check the build flags.** Review the `configure` options in the scripts against the new version's `./configure --help`, and any compiler flag that works around a toolchain problem (for example `-std=gnu17` for libiconv 1.17).
4. **Build twice.** Push the branch, then run each workflow (`Native: Windows x64`, `Native: Linux`, `Native: macOS`) two times from the Actions tab.
   - The two runs of each workflow must print identical hashes. If they don't, find out why before going on.
5. **Install the binaries.** Download the artifacts (`windows-x64`, `linux-x64`, `linux-aarch64`, `macos-x64`, `macos-aarch64`) and copy the binaries to the paths in the table above.
6. **Write the manifests.** Unpack each artifact into its own directory and run, with the commit and run URL of the second run:
```bash
   WORKFLOW_COMMIT=<commit the workflow ran at> \
   WORKFLOW_RUN_URL=https://github.com/doblon8/jzbar/actions/runs/<run id> \
   native/write-manifest.sh <platform> <artifact directory>
```
   The Linux and macOS workflows each produce two artifacts from one run, so use the same commit and run URL for both architectures. The commit must be pushed and available locally.
7. **Update the test.** Change the expected `ZBar.version()` string in `ZBarTest`.
8. **Licenses and notices.** Replace the license texts taken from the tarballs and regenerate the notices. *(To be completed when the notices generator is added.)*
9. **Check.** Run `native/check-manifests.sh` locally, then push and wait for CI. The test matrix runs on all five platforms.
10. **Commit** the binaries and the manifests together.

## Rebuilding without changing versions

Use this when you want to know whether the committed binaries still reproduce, for example after a runner image update.

1. Run the three workflows and compare the printed hashes with `native/manifest/*.manifest`.
2. If they match, nothing to do.
3. If they differ, compare the artifact's `toolchain.txt` with the manifest. A different compiler, linker, libc or SDK version explains a different hash. The packages are logged but not pinned (MSYS2, apt), so a package update changes bytes without any change in the scripts.
4. If the toolchain is identical and the hash differs, the build is no longer deterministic. Investigate before releasing anything.
5. Replace the committed binaries only for a reason. If you do, follow steps 4 to 10 above (the sources are unchanged).

## Changing the toolchain pins

- Linux container: `container:` in `.github/workflows/native-linux.yaml`, pinned by digest. The manifest records it.
- Actions: pinned by commit SHA in every workflow, with the version in a comment.
- Anything that changes the toolchain changes the manifest, so rebuild twice and regenerate the manifests.
